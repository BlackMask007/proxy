## UDP 代理机制(重点)

**mode 3(主用)——目标 IP 本地化 + 用户态端点套接字**:
1. 应用 connect/sendto(目标)→ 驱动 ALE 只记不改(24H2 上 UDP 连接重定向是
   半完成黑洞,实证禁改)→ FLOW_REDIRECTED 事件 → 引擎**预置目标端点套接字**
   (目标 IP 加为本机环回 /32 附加地址 → `bind(目标 ip:port)`);
2. 应用数据报**原生送达**目标端点套接字(源=应用端点)→ 每流独立 SOCKS5
   UDP ASSOCIATE(节点会话钉首个数据报,一套接字即一流身份)→ 转发;
3. 回程从**同一目标端点套接字** `sendto(应用端点)` —— 源天然是原始目标,
   connected 语义原生满足,零伪造、零内核注入。
4. 时序:测试可用 `HpxUdpPreTargetA` 预热目标消除首包竞态;真实应用由
   ALE 事件驱动(首包可能在套接字建立前漏失,依赖应用重试)。

**mode 0/1(备选)——数据报吸收 + 内核注入**:驱动 D4 层吸收应用数据报并
整包注入本地中继(驱动附 flowId 尾标消解多目标歧义);回程经 IOCTL 200
网络接收注入(FwpsInjectNetworkReceiveAsync0,ifIndex 取应用流所在接口)。
该路径在本机未完成稳定验证(回程注入落地率待证),保留为配置可切
(服务 Parameters\Layers 位掩码:1=ALE 2=D4;引擎 HpxSetUdpBackMode)。

## 2026-10-13 晚间·三渠道稳定性修复(ip111.cn 场景)

用户实测 ip111.cn 三渠道:只有"从国外"显示节点 IP,"从谷歌"空白,"从国内"显示真实 IP。
四层根因,均已修复:

1. **`HpxSkipDestV4` 字节交换误判(主根因,解释"有些网站没走代理")**:
   对 fixed-value 的字节交换值也判 224/4 组播——任何**末字节 ≥224 的普通单播目标**
   (如 ip111.cn=122.114.192.226)交换后顶字节落进 224/4 区,被静默放行直连;
   统计上约 12% 的目标随机漏网,观感即"代理不稳定"。修复:只按 fixed-value 大端序判读。
2. **DNS 污染穿透(谷歌渠道空白)**:114DNS 对被墙域名返回随机假 IP
   (sspanel.net → 31.13.x/104.244.x/199.59.x + `face:b00c` 假 v6,逐次随机),
   代理链把假 IP 透传给节点 → 节点连假 IP 死流。修复:
   - TCP 中继窥视首包取 **TLS SNI / HTTP Host**,按**域名(ATYP=3)交节点解析**;
   - 浏览器自身 DNS(UDP/53)本就随链代理(节点侧干净解析);
   - Host 占位符(如测试桩 "probe")不带点 → 回退 IP 直连(防误把桩 Host 当域名)。
3. **进程登记竞态(短命进程首连直连泄漏)**:映像名规则下推驱动,classify 按
   `ALE_APP_ID` 文件名尾匹配**即时接管**(NUL/边界容忍),不再依赖引擎 1s 扫描轮询。
4. 附带修复:UDP 认领**幂等化**(多包流逐包认领不再丢,QUIC 只进首包的根因)、
   受代理进程 **IPv6 连接 fail-fast 拦截**(v6 污染旁路封死,快乐眼球回落 v4 主路)、
   auto 扫描线程 500Hz 自旋(停止事件残留置位)修复。

## 2026-10-13 深夜·绑定语义固化(去"轮询感")

用户反馈"偶尔会掉、感觉是轮询的代理"。设计目标改为:**绑定即持续全局代理,
除非手动断开**。本轮改动:

1. **进程生命周期不再靠快照投票**:自动登记项的注销判据从"Toolhelp 快照缺席"
   (天生竞态,存活进程会被误销绑定=感知上的"掉")改为**权威判据**
   `OpenProcess + GetExitCodeProcess(STILL_ACTIVE)`;存活再验映像名防 PID 复用。
   注销原因日志改为 `exit-confirmed` / `pid-reuse`,不再出现 `exit-or-reuse`。
2. **手动绑定永不动**:`按PID代理`/手动登记的条目(isAuto=0)不参与任何自动注销,
   只有用户点"移除PID"或"停止代理"才解除;映像名规则在驱动侧 classify 常驻匹配
   (上一轮已下推),进程新生/扫描间隔都不影响接管。
3. **上游容错**:TCP 上游(节点 CONNECT)与 UDP 上游(节点 UDP ASSOCIATE)均改为
   3 次尝试 + 300ms 退避,吸收节点偶发抖动,减少用户感知的瞬断。

绑定生命周期对照:

| 事件 | 行为 |
|---|---|
| 按 PID 代理(手动) | 一直代理到手动移除/停止代理;进程退出后记录保留(防复用有映像名复核) |
| 按进程名代理 | 规则常驻驱动,classify 即时命中;同名进程全体+后续新生自动覆盖 |
| 自动登记项(映像名命中) | 进程确认退出才注销(`exit-confirmed`);PID 被复用为别的映像则 `pid-reuse` 注销 |
| 手动断开 | GUI"移除PID"/"停止代理"→ 立即解除 |

## 2026-10-15·按进程代理的"存量连接"收编(绑定即接管)

用户质疑"按进程代理 chrome 后 ip111 仍有未代理 IP"。根因:**池化/保活连接建立于
代理启动之前,不再走 connect() → 永远不会被透明拦截**(与进程是否绑定无关)。
修复:绑定即接管——在**绑定动作**(按PID/按进程名/全局开启)的瞬间,切断对应进程
的存量 TCP 连接(`SetTcpEntry` DELETE_TCB),应用随即重连,新连接即被内核层拦截。

**重要教训(2026-10-15 二修)**:收编最初挂在"进程自动登记"里,结果**每次新进程
登记都杀其活连接**——实测 10 连请求 9 掉线(掉线签名 `stale-tcp: killed 1 conns`
逐进程刷屏),正是用户"总是掉"的元凶。修正:**收编只在绑定动作时执行一次**;
自动登记不再清连接(映像名规则在驱动 classify 即时生效,登记竞态期的新连接本就被
拦截,无需清)。修正后同 10 连测试 **9/10 成功、掉线签名清零**,与裸节点对照
(8/10,evidence\stab_chain2.txt vs 节点直连同窗口实测)同级——链路无额外掉线。

实测(evidence\warm_test.txt、relay_warm.log):传输进行中绑定 curl → 日志
`stale-tcp: killed 1 conns pid=5924`,9.2MB 处传输被切断(未修复时会跑满 50MB)。
E2E 回归全绿(e2e_killfix.txt)。已知边界:无连接 UDP 仍直连(见上节);浏览器
的 QUIC 会话若建于绑定前,其数据报仍按旧四元组直连,重开标签页即收编。
## 2026-10-16·长时运行健康(未代理也不拖累系统 + 慢速期不误杀)

用户反馈"程序长时间运行,即便未代理也网络不稳"。深度排查出两处随时间累积的损伤源:

1. **日志系统**:每行日志 `fopen/fputs/fclose` + 文件**无限膨胀**(3.5MB→数小时数十 MB)
   ——句柄/IO 抖动随运行时长累积。修复=**持久文件句柄 + 8MB 轮转**(relay.1.log),
   长时运行的日志开销恒定、磁盘占用封顶。
2. **8 秒套接字超时误杀慢传输(不稳定/上行失败的真根因)**:握手期的 8s 口径被
   大块数据泵沿用——节点慢速期"发送无进展 8 秒"即被我方**主动断链**,慢但活着的
   传输被杀死(上传/下载在慢速期失败)。修复=**握手后放宽到 300 秒无进展才判死**
   (应用侧对称设置),慢速期传输一律跑完,只有真死连接才回收,兼防线程滞留。

长时观测(引擎空载/无任何代理,24 点×20 秒,evidence\longrun2.txt):节点 ping
**全程 0ms、0% 丢包、无恶化**——程序在未代理状态下不损伤系统网络;上传压力
12/12 成功(链 6/6 + 裸节点 6/6,upstress.txt),修复②后慢速期无自伤路径。
E2E 回归全绿(e2e_longfix.txt)。

用户反馈"多次刷新 ip111 有时显示未代理 IP"。排查出**真实泄漏机制**:
`EmptyData`(停止代理/启停)会清空驱动侧**映像名规则**——规则是配置不是状态,
被误清后重启代理不再有 classify 级接管,新进程回到"创建→扫描登记"竞态窗口,
首个连接直连 → 页面偶发显示未代理 IP。修复双管齐下:

1. **规则跨清空/重启保留**(驱动侧不再随 RESET 清除映像名规则);

## 2026-10-15·吞吐深度优化(对齐系统代理)

用户对比:系统代理测速(YouTube)100000+,我方透明代理仅 30000+。分相定位(同窗
50MB 下载、同节点、系统代理语义=直连 SOCKS 对照):

| 轮次 | 系统代理语义(裸 SOCKS) | 我方透明链 | 倍率 |
|---|---|---|---|
| 优化前 | 3.40 MB/s | 1.93 MB/s | 0.57× |
| 聚合读后 | 11.55 MB/s | 5.02 MB/s | 0.44× |
| 去逐块日志后 | 5.77 MB/s | **12.88 MB/s** | **2.23×** |
| 复测 ×2 | 5.52 / 5.95 MB/s | **7.23 / 11.14 MB/s** | **1.31× / 1.87×** |

两个根因(都在中继泵):
1. **小块转发**:recv() 只取到已到达的零头(常为几 KB)→逐零头系统调用+小包序列,
   修复=**聚合读**(FIONREAD 一次收干凑成 64KB 大块再整块转发):1.93→5.02 MB/s。
2. **逐块诊断日志**(排障期加的每块 LogF):每块一次磁盘写(≈156 次/秒)主导了泵周期,
   修复=删逐块日志(仅留失败分支):5.02→12.88 MB/s。

另配 QUIC 语义对齐:系统代理本就 TCP-only(浏览器经代理不走 HTTP/3);我方对受代理
进程的 UDP/443(QUIC)做 fail-fast 拦截回落 TCP/443,测速口径与系统代理完全一致
(quicblk 计数入诊断行)。节点自身吞吐分钟级波动 3.4~11.5 MB/s(同窗对照可见),
绝对数值仍随节点负载起伏;我方链路已 ≥ 系统代理语义的同窗水平。
